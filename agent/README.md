# Insight Scout — 検証可能なエージェントループ・ハーネス

このディレクトリは、以下の一次ソースを順に確認したうえで設計した
**「エージェントループ（ハーネス）そのものを検証するためのエージェント」** です。

## なぜ「ループの検証」がエージェントの本体なのか

一次ソースが共通して示しているのは次の 1 点です:

> **エージェントの品質はモデルだけでは決まらない。モデルを取り囲む実行系
> （ハーネス＝エージェントループ）の設計が、同じモデルの成績を数倍変える。**

- **Codex as a platform**（OpenAI Developers Blog, 2026-08-19）:
  ハーネスとは「タスクを理解し、コンテキストを維持し、情報を調べ、ツールを呼び、
  進捗を公開し、失敗を処理し、必要なら人間の承認を求め、有用な結果を返す」
  実行系である、と定義しています。
- **2つの設定でARC-AGI-3のスコアが3倍に**(OpenAI, 2026-07-29):
  モデル(GPT-5.6)を一切変えず、ハーネスの 2 設定 —
  **(1) 行動のたびに推論を破棄しない（推論の保持）**、
  **(2) コンテキスト超過時に最古のメッセージを黙って切り捨てず要約する（コンパクション）**
  — を直しただけで、公開タスクのスコアが **13.3% → 38.3%（約3倍）**、
  出力トークンは **約1/6** になりました。
- **Codex オープンソース部品ガイド / openai/codex リポジトリ**:
  同一のハーネスを `codex exec`（有界・非対話・構造化出力）、SDK（プログラム制御）、
  `app-server`（永続会話・イベントストリーム・承認ハンドリング）という部品として
  公開しており、「ハーネスは製品から独立に再利用・検証できる部品である」ことを
  示しています。

そこでこのエージェントは、**ハーネスをモデルから完全に分離**し、
スクリプト駆動のモックモデルで**ループの性質そのものを決定論的に検証**できる
構成にしました。APIキーもネットワークも不要で `npm run agent:validate` が通ります。

## 実行方法

```bash
npm install

# ① 検証スイート（モックモデル・決定論的・APIキー不要）← まずこちら
npm run agent:validate

# ② 実モデルでのデモ（要 ANTHROPIC_API_KEY または `ant auth login`）
npm run agent:demo
```

## あなたに検証してほしい観点（V1〜V8）

`agent/src/validate.ts` の各セクションが 1 観点に対応します。
コードを読み、意地悪な改変（後述）でスイートが正しく落ちることまで確認して
もらえると、ハーネスの検証として完結します。

| # | 観点 | 由来する一次ソース |
|---|------|--------------------|
| V1 | 基本ループ: ツール往復と構造化された完了 | Codex as a platform / codex exec |
| V2 | 並列ツール呼び出しの結果が 1 バッチで返る | ハーネス一般 |
| V3 | 有界実行: `maxTurns` で必ず停止する | codex exec（bounded run） |
| V4 | **推論の保持**: ON なら前ターンの推論が次リクエストに含まれる | ARC-AGI-3 設定 1 |
| V5 | **コンパクション**: 要約は序盤の重要事実を保持し、切り捨て（アンチパターン）は失う | ARC-AGI-3 設定 2 |
| V6 | 承認ゲート: 却下は副作用を防ぎ、ループはクラッシュしない | Codex approval modes |
| V7 | 失敗処理: ツール例外はエラー結果として返り、モデルが回復できる | Codex ハーネス定義 |
| V8 | イベントストリーム: 進捗が正しい順序で観測できる | codex app-server |

### 変異テスト（推奨）

スイートが「本当に検証しているか」を確かめる最短の方法は、ハーネスを壊して
スイートが落ちることを見ることです。例:

- `loop.ts` の `stripReasoning` を常に適用する → **V4 が落ちる**
- `compaction.ts` の `compactBySummarize` で `head` を含めない → **V5a が落ちる**
- `loop.ts` の承認却下時に `return` せずツールを実行する → **V6 が落ちる**
- `executeTool` の `try/catch` を外す → **V7 がクラッシュ検出で落ちる**
- `while (turn < maxTurns)` を `while (true)` にする → **V3 が落ちる**

## 構成

```
agent/
├── README.md                 ← 本ファイル
└── src/
    ├── types.ts              コア型定義（モデル非依存）
    ├── loop.ts               エージェントループ本体（ハーネス）
    ├── compaction.ts         コンテキスト管理（要約 / 切り捨て比較用）
    ├── tools.ts              アナリティクス・ドメインのツール群
    ├── validate.ts           検証スイート（V1〜V8）
    ├── demo.ts               実モデルでのデモ実行
    └── model/
        ├── mock.ts           スクリプト駆動モデル（決定論的検証用）
        └── anthropic.ts      Claude API アダプタ（claude-opus-5）
```

### 設計上の対応関係

- `ModelClient` インターフェース（`types.ts`）— ハーネスとモデルの分離。
  ARC-AGI-3 の教訓「ハーネスはモデルと独立に評価できる」の実装形。
- `retainReasoning`（`loop.ts`）— 推論を履歴に保持し次リクエストへ戻す。
  実モデル接続時は thinking ブロックを含む生コンテンツの逐語エコーバックに対応
  （`model/anthropic.ts`）。OFF にすると ARC-AGI-3 で問題だった挙動を再現できる。
- `compaction: "summarize" | "truncate" | "off"`（`compaction.ts`）—
  `truncate` は比較検証のために意図的に残したアンチパターン。
  `summarize` は先頭のタスク指示と `pinnedFacts` を必ず保持する。
- `approvalPolicy` + `requiresApproval`（`loop.ts` / `tools.ts`）—
  副作用を持つツール（`save_report`）だけ承認を要求。却下はクラッシュではなく
  エラー結果としてモデルに返り、ループは継続する。
- `AgentEvent` ストリーム（`types.ts`）— `onEvent` で全イベントが順序どおり
  流れる。app-server がクライアントにイベントを配信する構造の縮小版。
- `TaskResult`（`types.ts`）— `codex exec` に倣い、必ず構造化された結果
  （status / output / turns / events / history）で終わる。

## 制限事項

- モックモデルは「ハーネスの検証」に必要な最小限であり、モデルの賢さは検証しない
  （それは意図的な設計で、一次ソースの主張そのもの）。
- トークン推定は文字数ベースの近似。実運用では各 API の usage を使うべき。
- 実モデルデモのコンパクションはクライアント側実装。Claude API にはサーバー側
  コンパクション（beta）もあり、実運用ではそちらの利用も検討できる。
